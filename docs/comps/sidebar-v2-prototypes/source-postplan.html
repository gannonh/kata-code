Sidebar v2 — five concepts

A rethink of the T3 Code thread sidebar: recency-first, project demoted to metadata, every thread a multi-line chunk with room for real context, and active work never hidden behind “show more”. All mock data below is synthetic fixture content so the concepts read true without embedding live workspace metadata.

What the data can already tell us

From OrchestrationThreadShell, sessions, turns, activities, and checkpoints — split by what the sidebar shows today vs. what it silently drops on the floor.

Shown today (barely)

  • Status pill Working / Connecting / Pending Approval / Awaiting Input / Plan Ready / Completed-unseen Sidebar.logic.ts
  • Relative time last user message latestUserMessageAt
  • PR state icon only; number + title hidden in tooltip vcs.status
  • Worktree icon only; path in tooltip worktreePath
  • Terminal / port tiny icons terminalSessions
  • Remote env cloud icon environmentId

Available but hidden

  • Live activity what the agent is doing right now thread activities
  • Elapsed time how long the current turn has run latestTurn.startedAt
  • Session errors a dead session shows nothing today session.lastError
  • Diff stats +adds/−dels, files touched per turn checkpoints
  • Last message snippet of the latest assistant reply messages
  • Model / provider fable-5 vs gpt-5.6-sol, effort modelSelection
  • Branch name currently tooltip-only branch
  • Plan mode interaction mode of the thread interactionMode
Pending Approval — blocked on you, highest priority Awaiting Input — agent asked a question Plan Ready — plan waiting for review Working — running, show what + for how long Done · unseen — finished since you last looked Failed — session error, invisible today  Idle — seen, settled, quiet

The straightforward evolution: one recency-sorted list of three-line cards. A colored edge rail makes state scannable as a vertical strip; the middle line always answers “what is it doing?”.

How it works

  • Line 1: title. Line 2: status verb + live activity (the “what is it doing” line). Line 3: project chip · branch · model · time.
  • Left rail color = state; skimming the rail column reads like a status strip.
  • Blocked threads swap the timestamp for “waiting Xm” — how long you've been the bottleneck.
  • Failed sessions finally visible (red rail + error text).

Trade-offs

  • Closest to a drop-in replacement; one list, no sections, dead simple mental model.
  • Every complaint addressed with zero new interaction patterns.
  • ~64px per card → roughly 10 threads per screen. Less overview than v1.
  • Blocked items can still drift down the list as other threads update.

How it works

  • The latest assistant message is the context line — no invented summaries, just what the agent last said.
  • Unread semantics: bold title + colored status dot on the favicon until you visit (driven by lastVisitedAt, which already exists).
  • Project = the avatar. Recognizable at a glance without a group header.

Trade-offs

  • Zero-learning-curve mental model; triage habits transfer from email.
  • Snippets make “which thread was that?” disappear — titles no longer carry all the weight.
  • Snippets of streaming messages churn; needs debounce or “sentence-stable” truncation.
  • Tallest rows of any concept (~72px); worst thread-per-screen density.

How it works

  • Three tiers: Needs you (sorted by wait time), Running, Recent (recency). Tiers are state-driven — threads move automatically.
  • Blocked cards carry the actual question/command and inline Approve / Review actions — clear the queue without opening threads.
  • Recent tier is deliberately compact; settled threads don't deserve tall cards.

Trade-offs

  • Directly optimizes the real workflow: “what is blocked on me right now?” Nothing actionable can ever scroll away.
  • Density where it belongs — big cards only for threads that earned them.
  • Threads jump between tiers as states change; needs careful animation to not feel chaotic.
  • Inline approve is a real safety/UX decision, not just a mock detail.

4Adaptive Density

One pure recency list, but rows change size with state: live threads render as rich cards with a spinner, current tool, and elapsed timer; settled threads collapse to slim one-liners. No sections, no tiers — the list breathes.

How it works

  • Row height is earned by state: live/blocked threads get the full card (spinner, current tool, live elapsed timer); settled threads collapse to one line.
  • Because active cards are naturally recent, the top of the list is your live dashboard and the tail is history — one sort, no sections.
  • Live timer (14m 22s) doubles as a health check: a “2h” working thread is visibly stuck.

Trade-offs

  • Best density-to-signal ratio of all five; history stays as compact as v1.
  • “Show more hides active work” is structurally impossible — active cards are big and at the top.
  • Rows resize when state changes; height animation must be tight or it feels jumpy.
  • A slim row shows less than v1 does today (no status text) — relies on the dot.

5Ops Grid

The power-user take: a dense two-line monospace ledger, like a fleet dashboard. Fixed columns — status word, branch, PR, diff, model — so your eyes learn positions, not layouts. Highest information per pixel.

How it works

  • Two fixed lines: title + time, then a columnar meta line — STATUS · payload · branch (⌥ = worktree) · model. Glyphs: ◆ approve, ● running, ? input, ▤ plan, ✓ done, ✕ error.
  • Attention states get a tinted row background instead of taller cards — density never changes.
  • Cross-project threads tint the title (file-host in blue) instead of using chips.

Trade-offs

  • ~15 threads per screen with full context — beats v1's density while showing 4× the data.
  • Fixed column positions make scanning nearly subconscious once learned.
  • Aesthetically opinionated (terminal vibe); diverges from the rest of the app's visual language.
  • Learning curve: glyphs and abbreviations must be memorized.

Shared decisions across all five

Locked in

  • Recency sort one global list; project becomes a chip/avatar/tint, never a group header
  • No “show more” nothing actionable is ever collapsed; long tails just scroll (virtualized)
  • Status is text the “what is it doing” line is first-class, not a tooltip
  • Errors surface session.lastError finally gets a state (red), fixing today's silent failures
  • Waiting-on-you time blocked threads show how long they've been blocked, not last-message age

Open questions

  • Archive affordance hover action vs swipe vs context-menu only, per concept
  • Inline approvals (concept 3) approve from the sidebar is powerful but needs a safety story
  • Snippet churn (concept 2) streaming messages need stable truncation
  • Multi-env where the cloud/remote badge lives in each layout
  • Hybrid the likely ship: concept 4's adaptive density + concept 3's needs-you pinning + concept 1's meta row

Data provenance: thread titles, branches, models, statuses, diff stats, and message snippets are synthetic fixtures for design exploration. States such as approval, input, plan-ready, and failed are included so every state renders in every concept.
