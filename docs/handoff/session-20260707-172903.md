## Key Debugging Outcomes

### Relay/Auth

- Docker working while Vercel failed proved this was not a generic Relay token failure.
- Root causes were sequential delivery gaps:
  - Vercel sandbox server installed from npm and initially lacked local fixes.
  - Relay had a separate loopback-only origin check and required its own deploy path.
- Relay deployment is separate from npm stable/nightly package releases. Do not assume npm release updates Relay.

### Vercel Sandbox Server Delivery

- Vercel bootstrap installs `@kata-sh/code-cli` from npm.
- Local server changes used by Vercel sandboxes must be published to a stable/nightly npm release or provided through a dev override.
- `KATACODE_SANDBOX_CLI_TAG=nightly` is available for dev/UAT pinning.

### Snapshot UX

- Vercel `snapshot()` stops the sandbox VM and returns a `snapshotId`.
- The app now persists the returned snapshot id and shows it in lapsed state.
- If clicking Snapshot after booting from a snapshot returns the same id, the UI now says that explicitly.
- The user manually copied a snapshot id from the Vercel dashboard during UAT before the UI persisted it.

### Startup Console Noise

- Browser console errors like `POST http://localhost:<ephemeral>/api/auth/websocket-ticket net::ERR_CONNECTION_REFUSED` came from startup auto-connecting stale local sandbox saved-environment records.
- `syncSavedEnvironmentConnections()` now skips auto-connect for local sandbox records while preserving auto-connect for managed Relay/SSH records.

## UX Direction Agreed With User

The user wants to converge the concepts:

- Current **Sandbox Environments** and **Remote Environments** sections are awkward and disconnected.
- A sandbox should not appear once as a config and again as a remote connection.
- The top-level UX should be one **Environments** section.
- The Add Environment modal already supports **Remote Link** and **SSH**.
- Expand that modal with:
  - **Remote Link**: current headless/pairing-code flow.
  - **SSH**: current SSH flow.
  - **Docker Container**: current Docker sandbox config.
  - **Cloud Provider**: provider-backed sandbox config.
- Inside **Cloud Provider**, expose a provider dropdown:
  - initially `Vercel Sandbox`
  - later other providers can be added without new top-level cards.
- Main list row should be one row per environment with:
  - type badge: `remote`, `ssh`, `docker`, `vercel`
  - lifecycle/status badge: `connected`, `running`, `stopped`, `lapsed`, `failed`
  - expand/edit controls appropriate to type.
- The current sandbox row toggle is confusing. If kept, label it as `Enabled` and make its semantics concrete; otherwise remove it.
- Current remote/headless environments should become editable, not only connect/remove.

## Recommended Implementation Plan

Use a staged approach to reduce migration risk.

1. **Visual merge first**
   - Keep underlying settings/registry models mostly intact.
   - Render a single `Environments` section.
   - Match sandbox definitions to saved remote records by sandbox metadata / provider instance id.
   - Hide the duplicate remote row when it represents the same sandbox.
   - Show connection/lifecycle state on the merged row.

2. **Move creation flows**
   - Extend the existing Add Environment modal with `Docker Container` and `Cloud Provider`.
   - Reuse current sandbox add/config components instead of creating a second modal.
   - For Cloud Provider, put Vercel-specific fields below a provider dropdown.

3. **Edit all environment types**
   - Remote Link/headless rows should expand with editable label/URL/auth metadata where safe.
   - SSH rows should expand with current SSH fields.
   - Docker/Vercel rows should expand with current sandbox config fields and runtime env vars.

4. **Data model cleanup**
   - After the visual merge is stable, introduce a unified `EnvironmentDefinition` or equivalent.
   - Migrate existing `sandboxProviderInstances` + saved environment registry records carefully.
   - Avoid breaking existing UAT state.
